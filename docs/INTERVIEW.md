# RAG 智能问答系统 - 面试级项目介绍

## 一、项目概述

### 1.1 项目背景

随着大语言模型（LLM）在各行业的广泛应用，如何让AI能够基于企业私有文档或最新知识进行问答成为一个重要课题。RAG（Retrieval-Augmented Generation，检索增强生成）技术应运而生，它通过结合信息检索和文本生成来解决这个问题。

**本项目是一个完整的、生产级的 RAG 智能问答系统**，实现了从文档上传、智能分块、向量检索、混合搜索到AI问答的完整流程。

### 1.2 项目目标

1. **学习目标**：深入理解 RAG 技术的核心原理和工程实现
2. **面试展示**：展示全栈开发能力、架构设计能力和问题解决能力
3. **实际应用**：提供可直接使用的智能问答解决方案

## 二、技术架构解析

### 2.1 整体架构

```
用户问题 → 文本向量化 → 向量数据库检索 → 混合检索融合 → Rerank重排 → Prompt构建 → LLM生成 → 回答
```

### 2.2 核心模块详解

#### 2.2.1 文档处理模块 (`document_processor.py`)

**功能**：解析 PDF、TXT、Markdown 等格式文档，提取文本内容并智能分块。

**技术要点**：
- **PDF 解析**：使用 `pypdf` 库提取 PDF 文本
- **文本清洗**：正则表达式过滤无效字符，统一空白符
- **智能分块**：基于句子边界切分，保证语义完整性
- **重叠窗口**：相邻块之间保留重叠内容，避免上下文丢失

**面试亮点**：
> 问：为什么要进行文本分块，而不是直接处理整个文档？
>
> 答：主要有三个原因：1) LLM 有上下文长度限制（Context Window），无法一次处理超长文档；2) 精准检索需要细粒度的匹配，全文档检索容易引入噪声；3) 合理的分块大小可以平衡检索精度和上下文完整性。我的实现中默认 500 字符为一个块，相邻块有 50 字符的重叠。

#### 2.2.2 向量化模块 (`embedder.py`)

**功能**：将文本转换为高维向量表示，捕捉语义信息。

**技术要点**：
- **模型选择**：使用 BAAI/bge-large-zh-v1.5 中文优化模型
- **向量归一化**：L2 归一化确保向量长度一致，便于余弦相似度计算
- **批处理优化**：支持批量向量化，提升处理效率

**面试亮点**：
> 问：Embedding 向量的维度是固定的吗？维度高低有什么影响？
>
> 答：是的，由模型决定。BGE-large 生成的向量维度是 1024。维度越高，表达能力越强，但存储和计算成本也越高。维度太低会丢失语义信息，太高则增加计算开销且可能引入噪声。在实际项目中，需要在精度和性能之间找到平衡。

#### 2.2.3 向量数据库 (`vector_store.py`)

**功能**：存储文档向量，支持高效的相似度检索。

**技术要点**：
- **数据库选择**：Chroma - 轻量级、无服务器、适合部署
- **相似度度量**：余弦相似度（Cosine Similarity）
- **元数据存储**：每个向量关联文档ID、来源文件等信息

**面试亮点**：
> 问：Chroma 是如何实现高效检索的？
>
> 答：Chroma 底层使用 HNSW（Hierarchical Navigable Small World）图算法实现近似最近邻（ANN）搜索。HNSW 通过构建多层图结构，用跳表思想实现 O(log n) 的检索复杂度，同时保证高精度。相比暴力搜索 O(n) 的时间复杂度，HNSW 在大规模向量场景下优势明显。

#### 2.2.4 混合检索模块 (`bm25.py`)

**功能**：结合向量检索和关键词检索，提升召回率。

**技术要点**：
- **BM25 算法**：经典的稀疏检索算法，基于词频和文档频率计算相关性
- **混合策略**：α 参数控制向量检索和 BM25 的权重比例
- **分数归一化**：将两种检索的分数归一化到同一尺度后融合

**面试亮点**：
> 问：为什么需要混合检索？向量检索不够用吗？
>
> 答：向量检索擅长语义匹配，但对专有名词、精确短语匹配效果较差。例如用户搜索"Transformer 架构"，向量检索可能召回"注意力机制"相关但没有精确提到"Transformer"的内容。而 BM25 基于关键词匹配，能精准命中用户输入的术语。混合检索结合两者优点，既能理解语义，又能精准匹配关键词，显著提升召回率。

#### 2.2.5 Rerank 重排序模块 (`reranker.py`)

**功能**：对初始检索结果进行精细排序，提升相关性。

**技术要点**：
- **模型选择**：BAAI/bge-reranker-large
- **Cross-Encoder**：将 query 和 document 一起输入，输出相关性分数
- **重排粒度**：比向量检索更精准，但计算成本更高

**面试亮点**：
> 问：为什么不直接用 Reranker 做检索，而要先向量检索再 Rerank？
>
> 答：主要是性能和成本的权衡。Reranker 是 Cross-Encoder 架构，需要对每个 query-document  pair 单独计算，计算复杂度是 O(n)，不适合大规模检索场景。向量检索先用 HNSW 在百万级向量中快速召回 top-k（时间复杂度 O(log n)），再用 Reranker 对少量候选结果精细排序。这是一种级联检索策略，在精度和效率之间取得平衡。

#### 2.2.6 LLM 服务模块 (`llm_service.py`)

**功能**：调用大模型生成最终回答。

**技术要点**：
- **API 集成**：支持通义千问（Qwen）和豆包（Doubao）
- **Prompt 工程**：设计高质量的 Prompt 模板
- **异常处理**：API 调用失败时提供优雅降级

## 三、数据库设计

### 3.1 SQLite 表结构

```sql
-- 知识库表
knowledge_bases (
    id PRIMARY KEY,
    name UNIQUE,
    description,
    created_at,
    updated_at
)

-- 文档表
documents (
    id PRIMARY KEY,
    knowledge_base_id REFERENCES knowledge_bases,
    filename,
    file_path,
    file_size,
    file_type,
    status,        -- pending | processing | completed | failed
    chunk_count,
    created_at,
    processed_at
)

-- 对话会话表
chat_sessions (
    id PRIMARY KEY,
    title,
    knowledge_base_id REFERENCES knowledge_bases,
    created_at,
    updated_at
)

-- 聊天消息表
chat_messages (
    id PRIMARY KEY,
    session_id REFERENCES chat_sessions,
    role,          -- user | assistant
    content,
    sources,       -- JSON 格式存储参考来源
    created_at
)
```

### 3.2 面试要点

> 问：为什么选择 SQLite 而不是 PostgreSQL/MySQL？
>
> 答：本项目定位是轻量级、易部署的知识库系统。SQLite 的优势：1) 零配置，无需独立数据库服务；2) 文件型数据库，数据迁移只需复制文件；3) 对于中小规模数据（< 100GB），性能与 RDBMS 相当；4) 部署到 Render 等平台时无需额外配置。如果是生产级大规模应用，我会考虑 PostgreSQL + pgvector 的组合。

## 五、面试常见问题

### Q1: RAG 和 Fine-tuning 的区别？如何选择？

**回答要点**：
- Fine-tuning 是让模型"记住"知识，需要大量标注数据和GPU资源
- RAG 是让模型"查询"知识，实时检索，更新知识不需要重新训练
- RAG 适合：知识频繁更新、需要可解释性、数据隐私敏感
- Fine-tuning 适合：任务固定、数据丰富、延迟敏感场景

### Q2: 如何评估 RAG 系统的效果？

**回答要点**：
- **检索指标**：Precision@K, Recall@K, MRR, NDCG
- **生成指标**：BLEU, ROUGE, 人工评估
- **端到端**：问答准确率、用户满意度
- 本项目提供：相似度分数展示，让用户可解释评估

### Q3: 遇到检索结果不准确怎么办？

**回答要点**：
1. 检查文档预处理是否正确
2. 调整分块大小（太大/太小都不好）
3. 尝试不同的 embedding 模型
4. 优化混合检索的 alpha 参数
5. 增加 Rerank 步骤提升精度

### Q4: 如何处理实时性要求高的场景？

**回答要点**：
- 文档更新频率：如果知识更新频繁，需要增量更新向量索引
- 缓存策略：对常见问题使用 LRU 缓存
- 异步处理：文档处理放入任务队列，不阻塞主流程
